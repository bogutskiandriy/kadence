# ADR-003: Нуль рантайм-залежностей у ядрі

- **Дата:** 2026-09-02
- **Статус:** прийнято
- **Область:** стек

## Контекст

Після ADR-001 на всю роботу CLI лишається 160 мс. Заміряно вартість самого лише `import` кандидатів (best of 3, Node v25.8.2, без бандлінгу):

| Пакет | Імпорт | Розмір |
|---|---|---|
| `zod` 4.5.4 | **23.6 мс** | 5.8 МБ |
| `commander` 15.0.0 | 17.1 мс | 207 КБ |
| `yaml` 2.9.0 | 13.5 мс | 686 КБ |
| `gray-matter` 4.0.3 | 13.0 мс | 39 КБ |
| `ulidx` 2.4.1 | 11.5 мс | 66 КБ |
| `ulid` 3.0.2 | 10.1 мс | 69 КБ |
| `citty` 0.2.2 | 8.3 мс | 35 КБ |
| `picocolors` 1.1.1 | 7.7 мс | 6 КБ |
| `valibot` 1.4.2 | 5.0 мс | 1.8 МБ |
| `cac` 7.0.0 | **3.3 мс** | 41 КБ |

Один лише `zod` коштує 15% усього бюджету — за валідацію об'єкта з семи полів.

Тому заміряно, скільки коштують власні реалізації того самого:

| Власна реалізація | Вартість імпорту | Пропускна здатність | Коректність |
|---|---|---|---|
| ULID (26 симв., Crockford base32) | **0 мс** | 100k за 132 мс | сортування за часом — так; 50k унікальних без колізій |
| Валідація події (7 полів, type guards) | **0 мс** | 100k за 17.5 мс | ловить усі 6 класів помилок |

Обидві — приблизно по 30 рядків.

## Розглянуті варіанти

| Варіант | Плюси | Мінуси |
|---|---|---|
| `zod` для схеми + `ulid` | Схема як єдине джерело типів; вивірена спільнотою реалізація | 33.7 мс імпорту разом — 21% бюджету за ~60 рядків функціональності |
| `valibot` для схеми | Модульний, tree-shakable, 5 мс | Все одно платимо за узагальнений рушій там, де форма події фіксована й не змінюється в рантаймі |
| Власні ULID + валідація | 0 мс; повний контроль; жодних CVE й оновлень у ланцюжку постачання | ~60 рядків, які треба покрити тестами й підтримувати самим |

## Рішення

**Ядро (модулі M1–M5) не має жодної рантайм-залежності.** ULID і валідація подій — власні, під тестами.

Це не «not invented here». Аргумент рівно один і він вимірюваний: узагальнені бібліотеки валідації створені для схем, що описуються в рантаймі й змінюються. У нас форма події фіксована в типах на етапі компіляції, а перевірка потрібна рівно на межі — коли читаємо файл, який міг зіпсувати людина або merge. Для цієї задачі рушій на 5.8 МБ не дає нічого, чого не дає функція на 20 рядків, зате коштує п'яту частину бюджету запуску.

ULID обрано (замість UUIDv4) з окремої причини: перші 10 символів — це мітка часу в Crockford base32, тож лексикографічне сортування ідентифікаторів збігається з хронологічним. Порядок подій стає властивістю самого ID і не залежить від того, наскільки розійшлися системні годинники на різних машинах — це прямо закриває edge case з розділу 7.3 PRD.

## Наслідки

- Позитивні: ~34 мс бюджету збережено; `npm audit` на ядрі не має що показати; ланцюжок постачання складається з нуля ланок.
- Ціна рішення: ~60 рядків криптографічно чутливого (ULID використовує `node:crypto`) і валідаційного коду — наш обов'язок тестувати. Обидві реалізації мають бути покриті property-тестами, а не лише прикладами.
- Що доведеться переглянути: якщо схема подій стане розширюваною плагінами (користувацькі типи подій із власними полями), фіксована валідація перестане працювати — тоді повертаємось до `valibot` як найдешевшого з рушіїв.
