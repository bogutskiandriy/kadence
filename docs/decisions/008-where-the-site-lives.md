# ADR-008: Де живе лендінг

- **Дата:** 2026-09-03
- **Статус:** прийнято
- **Область:** репозиторій, маркетинг, деплой

## Контекст

Ухвалено робити лендінг: Next.js + Tailwind + Motion, хостинг Vercel, власний домен. Постає питання, де лежить його код — у цьому репозиторії чи в окремому.

[ADR-007](007-what-goes-into-git.md) уже дав правило й одне питання для кожного нового файлу: **чи зможе хтось інший відтворити або зрозуміти продукт без нього?** Лендінг цю перевірку не проходить — CLI повністю зрозумілий і відтворюваний без жодного рядка сайту.

Масштаб теж має значення. Next.js із Tailwind і Motion — це власний `package.json`, власний lock-файл, власний CI, конфіги збірки й, найголовніше, **бінарні асети**: відео демо, постери, og-картинки. У репозиторії, який щойно скоротили з 491 файла до 94 саме заради того, щоб клон не тягнув чужого, mp4 на кілька мегабайт — рівно та сама помилка в новій обгортці.

## Розглянуті варіанти

| Варіант | Плюси | Мінуси |
|---|---|---|
| Папка `site/` у цьому репозиторії | Числа й копія версіонуються разом із продуктом; один PR міняє обидва | Порушує ADR-007; відео в git продукту; діфф продукту тоне в маркетингу; на Vercel потрібні Root Directory та Ignored Build Step |
| **Окремий репозиторій `kadence-site`** | Репозиторій = продукт, як і вирішено; окремий проєкт Vercel без обхідних налаштувань; issues і зірки продукту не змішуються з маркетинговими | Числа на сторінці можуть розійтися з тестами |
| Гілка `gh-pages` | Нуль нових репозиторіїв | Найгірше з обох: історія сайту в історії продукту, а працювати незручно |

## Рішення

**Окремий репозиторій `kadence-site`.** Продуктовий репозиторій лишається продуктом.

Аргумент «числа беруться з тих самих тестів» виявився слабшим, ніж здавався: у спільному репозиторії їх усе одно копіювали б руками. Тому ціну знімаємо явним механізмом, а не сусідством файлів:

1. У сайті всі числа лежать в одному файлі `content/facts.json` — кожне з полем `source` (шлях до тесту або документа, який його тримає).
2. У чек-лист релізу продукту додається рядок: **оновити `facts.json`, якщо змінилися розмір, час старту або дані probe**.
3. Коли це почне забувати — GitHub Action у продукті публікує бенчмарк як артефакт релізу, а сайт читає його при збірці. Робити наперед не варто: поки релізів мало, це складність без потреби.

## Наслідки

- Позитивні: `git clone` продукту й далі дає лише продукт; сайт вільно тягне будь-які залежності й асети, не питаючи дозволу в ADR-007; деплой на Vercel — стандартний, без Root Directory та Ignored Build Step.
- Ціна: два репозиторії замість одного, і числа треба свідомо синхронізувати.
- Що доведеться переглянути: якщо сайт зросте в документацію, згенеровану з коду (`--help`, схема JSON), — тоді генератор має жити в продукті, а сайт споживати його вивід як пакет чи артефакт. Переносити сайт назад це не привід.

## Поки репозиторію немає

Код готується в каталозі `site/` на диску, який **не потрапляє в git** цього репозиторію — так само, як `.claude/`. Коли каталог буде готовий, з нього робиться окремий репозиторій. Рядок у `.gitignore` існує саме для цього періоду й прибирається разом із каталогом.
