# Edge cases і поведінка при помилках

- **Дата:** 2026-09-02
- **Походження:** кожен випадок виведено з ромба в [потоках](user-flows.md), інваріанта в [станах](state-machine.md) або з реального спостереження

## Принципи

1. **Ніколи не звинувачувати користувача.** «Не знайдено активного спринту» — не «ви не створили спринт».
2. **Повідомлення = що сталося + чому + що робити.** Третя частина обов'язкова, і в ній має бути команда, яку можна скопіювати.
3. **Пошкоджені дані не зупиняють роботу.** Один битий файл не має ховати решту журналу.
4. **Ніколи не «щось пішло не так».** Якщо ми не знаємо причини — кажемо, який саме файл і яка операція.
5. **Помилки в `--json` — теж JSON.** Інакше агент отримає зіпсований потік.

## A. Середовище

| Ситуація | Поведінка | Повідомлення |
|---|---|---|
| Не git-репозиторій | Вихід 1, нічого не створюємо | `FlowIt живе всередині git-репозиторію, а тут його немає.` + `git init` |
| Команда до `init` | Вихід 1 | `.flowit/ не знайдено. Виконайте: npx flowit init` |
| `user.email` не налаштований | Вихід 1 | `Git не знає, хто ви — подію нема від кого записати.` + `git config user.email you@example.com` |
| **Зникла тека `events/2026-09/`** | **`mkdir -p` перед кожним записом, мовчки** | немає — це нормальний стан |
| `.flowit/` є, але порожня | Вважати ініціалізованою, журнал порожній | `Задач поки немає. Створіть першу: flowit task add "..."` |
| Немає прав на запис | Вихід 1 | `Не можу писати в .flowit/events/ — немає прав.` + шлях |
| Повторний `init` | Нічого не руйнуємо, вихід 0 | `FlowIt уже ініціалізовано.` |

**Про зниклу теку.** Git не версіонує порожні директорії, тому `events/2026-09/` зникає при перемиканні на гілку, де подій цього місяця не було. Під час спайку це відтворилося **двічі**. Тому `mkdir -p` при кожному записі — не оптимізація, а вимога, і її не можна «прибрати як зайву».

## B. Пошкоджені дані

| Ситуація | Поведінка | Повідомлення |
|---|---|---|
| Битий JSON в одній події | Пропустити, решту прочитати, порахувати | `Пропущено 1 пошкоджену подію: events/2026-09/01J8….json` (stderr) |
| Обрізаний файл (перерваний запис) | Те саме | те саме |
| Подія невідомого типу | Пропустити, **не помилка** | `Пропущено 2 події новішого формату. Оновіть FlowIt.` |
| `state.json` пошкоджений | Мовчки видалити й перебудувати | немає |
| `state.json` видалено вручну | Перебудувати | немає — **інваріант I6** |
| Понад 20% журналу пошкоджено | Вихід 1 | `Журнал пошкоджено серйозно: 34 з 120 подій нечитані.` + `git status`, `git checkout .flowit/` |

**Чому пропуск, а не падіння.** Журнал зливається автоматично й може містити події з майбутніх версій FlowIt. Падіння на невідомому типі зробило б оновлення в команді неможливим: перший, хто оновиться, зламає CLI решті.

Поріг у 20% розділяє «одна подія зіпсувалася» і «щось системно не так» — у другому випадку мовчати небезпечно.

## C. Операції Git

| Ситуація | Що відбувається | Поведінка |
|---|---|---|
| `git rebase` | Коміти переписані, **файли подій ті самі** | Працює. ULID незмінні, порядок за ULID зберігається |
| **`rebase` з `drop` коміту** | **Подія зникає з історії** | **Втрата даних.** Стан перерахується без неї — тихо й коректно з погляду журналу |
| `squash merge` | Усі події гілки в одному коміті | Працює без відмінностей |
| `cherry-pick` події | Подія з'являється у двох гілках з тим самим ULID | Дедуплікація за ULID при згортанні |
| `git revert` коміту з подією | Файл події видалено новим комітом | Стан перерахується без неї. **Це єдиний легальний спосіб «скасувати» подію** |
| Detached HEAD | Читання працює, запис теж | Попередження: `Ви не на гілці — подія може загубитися при перемиканні` |
| **`git worktree`** | Кожне робоче дерево має власну `.flowit/` | Шлях визначати від кореня **поточного** дерева, не від головного репозиторію |
| Shallow clone (`--depth`) | Журнал повний, бо це файли, не історія | Працює |
| `.flowit/` у `.gitignore` цілком | Журнал не комітиться | Попередження при `init`: `.flowit/ у .gitignore — сенс FlowIt втрачається` |

**Про `rebase --drop` треба сказати чесно:** ми не можемо це виявити. Подія просто зникає, і журнал лишається внутрішньо несуперечливим. Це прийнятна ціна за життя у git — але вона має бути в документації, а не з'ясовуватися користувачем самостійно.

**Про worktree.** У Backlog.md є відкрита issue #558 рівно про це: їхній MCP-сервер писав у головний репозиторій замість worktree. Помилка природна й дорога, тому фіксуємо правило заздалегідь.

## D. Конкурентність і час

| Ситуація | Поведінка |
|---|---|
| Два процеси пишуть одночасно (людина + агент) | Конфлікту немає: різні ULID → різні файли. Запис атомарний через temp + `rename` |
| Два процеси перебудовують `state.json` | Атомарний запис; програвший перезапише — вміст ідентичний |
| **Годинник відкотився назад** | ULID генерується **монотонно в межах процесу**: якщо новий час ≤ попереднього, інкрементується випадкова частина |
| Годинники різних машин розійшлися | Не має значення: порядок за ULID, не за `ts` — **інваріант I2** |
| Дві машини створили подію в ту саму мілісекунду | 80 біт випадковості; на 50 000 ULID колізій не було ([виміряно](../decisions/003-zero-runtime-deps-in-core.md)) |

## E. Доменні межі

| Ситуація | Поведінка | Повідомлення |
|---|---|---|
| `task move` неіснуючої задачі | Вихід 1 | `Задачі FLOW-99 немає.` + `flowit task list` |
| Перехід у той самий стан | Подію **не пишемо**, вихід 0 | `FLOW-42 вже in_progress.` |
| Невалідний перехід (`backlog` → `done`) | **Пишемо подію, дозволяємо** | `Задача перейшла з backlog одразу в done, минаючи in_progress.` |
| Задача в закритий спринт | Відхилити, подію зберегти | `Спринт 4 закрито 2026-08-30 — його velocity не переписується.` |
| `sprint close` без активного | Вихід 1 | `Активного спринту немає.` + `flowit sprint create "..."` |
| Задачі без оцінки при закритті | Закрити, попередити | `3 задачі без оцінки не увійшли у velocity.` + список |
| Порожній спринт | Закрити, velocity = 0 | `Спринт закрито. Жодної задачі не завершено.` |
| Дуже довга назва (>200 символів) | Обрізати в списку, повністю в `show` | немає |
| Назва з переносом рядка | Прийняти, екранувати при виводі | немає |

**Чому невалідний перехід дозволено.** Заборона змусила б людину робити два кроки заради формальності, а журнал усе одно зафіксує реальний намір. Ми попереджаємо, але не блокуємо: FlowIt описує роботу, а не керує нею.

## F. Агентський режим

| Ситуація | Поведінка |
|---|---|
| Помилка при `--json` | JSON у stdout: `{"schema":"flowit/v1","ok":false,"error":{"code":"NOT_FOUND","message":"..."}}`, код виходу той самий |
| Попередження при `--json` | Тільки stderr — stdout лишається чистим JSON |
| Агент не встановив `FLOWIT_SOURCE` | `source: "human"` за замовчуванням. **Не вгадуємо** |
| Агент пише сотні подій поспіль | Обмежень немає, але `state.json` перебудовується раз наприкінці |
| Невідомий прапорець | Вихід 2 + підказка найближчої команди |

## G. Масштаб

| Ситуація | Поведінка |
|---|---|
| 10 000+ подій | `state.json` обов'язковий: 6 мс проти 140 мс ([виміряно](../decisions/005-sync-io-and-snapshot.md)) |
| Робоча копія роздулася | Компакція в `events/archive/` — інакше 39 МБ на 10k подій |
| Опис задачі на мегабайт | Прийняти; описи — окремі файли, у журнал не потрапляють |

## Що перевіряється тестами

Розділи B, C і D повністю входять до набору «стійкість» у [SPEC.md](../../SPEC.md). Найважливіші три:

1. Видалення `state.json` не змінює стан (I6)
2. Зникла тека `events/` відновлюється при записі
3. Пошкоджена подія не ховає решту журналу
