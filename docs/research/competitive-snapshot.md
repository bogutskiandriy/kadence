# Competitive Research Snapshot

- **Дата:** 2026-09-02
- **Режим:** Just Enough — глибина по трьох гравцях, що справді загрожують

## 1. Scope

**Продукт:** FlowIt — управління проєктами всередині Git-репозиторію
**Категорія:** git-native / file-based трекери задач для розробників і AI-агентів
**Рішення, яке підтримує це дослідження:** чи існує захищена диференціація FlowIt і яким має бути зріз MVP — **Assumption**, виведено з контексту сесії, окремо не підтверджено
**Проаналізовані конкуренти:** Backlog.md, git-bug, git-issues

**Чому саме ці троє.** PRD (розділ 4.2) порівнював FlowIt із Jira, Linear і GitHub Issues — тобто з інструментами іншого класу. Прямі конкуренти, які вже роблять рівно те саме (трекер у файлах репозиторію, CLI, TUI, орієнтація на AI-агентів), у PRD **були відсутні повністю**. Це найсерйозніша прогалина документа.

## 2. Competitor Snapshots

### Конкурент: Backlog.md

- **Позиціювання:** «tool for managing project collaboration between humans and AI Agents in a git ecosystem» — **Факт** ([репозиторій](https://github.com/MrLesk/Backlog.md)). Формулювання практично збігається з нашим.
- **Релевантні можливості:** один Markdown-файл на задачу; CLI без конфігурації; TUI-канбан (`backlog board`); веб-UI з drag-and-drop (`backlog browser`); MCP-інтеграція з Claude Code, Gemini CLI, Codex, Kiro; три чекпоінти рев'ю — **Факт** (там же)
- **Імовірна сила:** 6.6k зірок, MIT, TypeScript/Bun — зріла реалізація приблизно 80% нашого запланованого MVP, включно з TUI, який ми плануємо лише на v0.1b — **Факт** (зірки й ліцензія) + **Висновок** (оцінка перекриття скоупу)
- **Імовірна слабкість:** немає спринтів, velocity й time tracking; конфлікти між гілками не розв'язані архітектурно — у їхньому власному беклозі висить задача `task-4.12` про конфлікти ID задач між гілками, а рекомендована стратегія — «робіть дрібні незалежні задачі», тобто обхід поведінкою — **Факт** (відсутність фіч у документації; наявність task-4.12)
- **Ключове джерело:** https://github.com/MrLesk/Backlog.md

### Конкурент: git-bug

- **Позиціювання:** децентралізований трекер багів, вбудований у Git — **Факт** ([репозиторій](https://github.com/git-bug/git-bug))
- **Релевантні можливості:** CLI + TUI + веб; мости синхронізації з GitHub і GitLab; 2632 коміти — **Факт**
- **Імовірна сила:** 10k зірок, найзріліший у категорії; справді розподілена модель — **Факт**
- **Імовірна слабкість, і вона принципова:** дані зберігаються **як git-об'єкти, а не файли робочої копії** («objects in a git repository (_not files!_)»). Тому `git checkout` на старий коміт **не** показує тодішній стан задач у файлах, а агент не може прочитати задачу як звичайний файл — потрібен їхній CLI. Ліцензія GPLv3 ускладнює комерційне вбудовування — **Факт** (модель зберігання, ліцензія) + **Висновок** (наслідки для агентів)
- **Ключове джерело:** https://github.com/git-bug/git-bug

### Конкурент: git-issues

- **Позиціювання:** «Issues that move with your code» — **Факт** ([сайт](https://steviee.github.io/git-issues/))
- **Релевантні можливості:** `.issues/` з Markdown + YAML frontmatter; один Go-бінарник; TUI-канбан на Bubble Tea; вивід у JSON; `.agent.md` для агентів; команди `issues next / claim / done`; branch-aware трекінг; двоспрямовані зв'язки — **Факт**
- **Імовірна сила:** Go-бінарник стартує за ~2 мс проти наших 40 мс на Node; `.agent.md` і `issues next` — це рівно той контракт для агента, який ми проєктували в M8 — **Факт** (фічі) + **Висновок** (порівняння старту, за ADR-001)
- **Імовірна слабкість:** зрілість і аудиторія невідомі — зірок не встановлено; спринтів немає; конфлікти не адресовані — **Висновок**, низька впевненість
- **Ключове джерело:** https://steviee.github.io/git-issues/

## 4. So What?

### Наслідки для продуктової стратегії

1. **Теза «ніхто не тримає задачі у файлах репо» — спростована.** Троє роблять це вже зараз, двоє з них мають TUI, а один — ще й веб-UI. Розділ 4.2 PRD треба переписати: FlowIt виходить не на порожнє поле, а в наявну категорію з лідером на 10k зірок. — **Факт**, висока впевненість
2. **Єдина захищена відмінність — append-only журнал подій.** Усі троє зберігають **змінюваний** стан (файл задачі редагується). Тому дві гілки, що чіпають одну задачу, дають конфлікт, а Backlog.md визнає це відкритою задачею `task-4.12`. Наш спайк показав нуль конфліктів у тому самому сценарії. Це не маркетингова відмінність, а архітектурна, і вона вимірювана. — **Факт** (їхній беклог; наші виміри), висока впевненість
3. **Другий диференціатор — спринти, velocity й estimate-vs-actual.** Немає в жодного з трьох. Разом із першим пунктом це дає позиціювання не «трекер у репо» (зайнято), а «журнал роботи команди в репо, з якого рахується правда про спринт». — **Факт** (відсутність фіч), середня впевненість

### Конкурентні ризики

1. **Backlog.md може закрити наш розрив швидше, ніж ми побудуємо продукт.** Додати append-only журнал до наявного інструмента з 6.6k зірок дешевше, ніж нам набрати аудиторію з нуля. — **Висновок**, середня впевненість
2. **Ми плануємо TUI аж на v0.1b, а в конкурентів він уже є.** Наш v0.1a — це CLI без борду, тобто свідомо гірший продукт, ніж наявні безкоштовні альтернативи. — **Факт** (їхні фічі vs наш скоуп), висока впевненість

### Продуктові можливості

1. **Спринти й velocity як точка входу, а не «ще одна фіча».** Категорія зайнята на рівні «список задач», але порожня на рівні «аналітика роботи команди». — **Висновок**, середня впевненість
2. **Міграція з Backlog.md і git-issues.** Обидва тримають Markdown із frontmatter — імпорт технічно дешевий, а їхні користувачі вже прийняли головну ідею й лишається лише один аргумент: конфлікти. — **Висновок**, середня впевненість

### Припущення, які треба перевірити

1. **Конфлікти в змінюваних файлах — це біль, який люди відчувають на практиці**, а не теоретична вада. Якщо команди справді пишуть дрібні незалежні задачі, як радить Backlog.md, наша єдина відмінність нікого не турбує. — **Припущення**, критичне
2. **Спринти й velocity потрібні аудиторії git-native інструментів.** Можливо, їх немає в усіх трьох саме тому, що ця аудиторія їх не хоче. — **Припущення**, критичне
3. **Оцінка зрілості git-issues.** Уся колонка тримається на їхньому сайті. Якщо проєкт активний і популярний, конкурентна картина гірша, ніж описано. — **Припущення**, потребує перевірки
