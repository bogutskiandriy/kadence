# Дослідження: лендінг для kadence

- **Дата:** 2026-09-03
- **Питання:** як має виглядати сторінка, що просуває kadence, і які меседжі на ній стоять
- **Метод:** розбір YC-фреймворку лендінгів + структурний аналіз чотирьох реальних сторінок dev-tool + звірка з [позиціонуванням](../product/positioning.md) і [конкурентним знімком](competitive-snapshot.md)
- **Статус:** рішення ухвалені 2026-09-03 — заголовок A (аналітика), демо з `kadence ui`. Копія: [landing-copy.md](../product/landing-copy.md)

## 1. Що каже YC-фреймворк

Джерело: [Win the First 5 Seconds: The YC Landing Page](https://www.thevccorner.com/p/win-the-first-5-seconds-the-yc-landing).

Головна теза: відвідувач за п'ять секунд вирішує «це для мене?». Конверсія медіанного лендінга — 6.6%, у топових 10–15%.

| Правило | Формулювання |
|---|---|
| Заголовок | *Outcome for [ICP] without [pain]* |
| Мова | рівень читання ≤ 8 клас; складні слова забирають ~24% конверсії |
| CTA | рівно один головний (attention ratio 1:1) |
| Демо | 10–60 с, показує **результат**, а не інтерфейс |
| Рух | статика замість каруселей — «карусель ховає твій найсильніший аргумент» |
| Швидкість | < 2 с завантаження |
| Доказ | логотипи й іменні відгуки **над згином**, не в підвалі |
| Заперечення | міні-FAQ поруч із CTA, не окремою сторінкою |

Канонічний порядок секцій: Hero → Problem/Transformation → How it works → Social proof → Pricing → Mini-FAQ → Footer.

## 2. Де цей фреймворк не працює для нас

Фреймворк написано для SaaS із тріалом і прайсингом. kadence — OSS CLI, і три з семи секцій у нас порожні або означають інше. Я подивився, що роблять справжні dev-tool лендінги.

| Сайт | Заголовок | Головний CTA | Чим доводить |
|---|---|---|---|
| [biomejs.dev](https://biomejs.dev/) | «One toolchain for your web project» | Get started + View on GitHub | «~35x faster than Prettier» на бенчмарку 171 127 рядків; 15 логотипів (AWS, Google, Vercel) |
| [bun.com](https://bun.com/) | «Bun is a fast JavaScript runtime & toolkit» | сама команда встановлення в hero | чотири бенчмарки стовпчиками; іменні цитати (Anthropic, Midjourney, Railway) |
| [zed.dev](https://zed.dev/) | «Your last next editor» | Download now + Clone source | три стовпи (Fast/Agentic/Collaborative), живий фід комітів як доказ активності |
| [Backlog.md](https://github.com/MrLesk/Backlog.md) | «Markdown-native Task Manager & Kanban visualizer for any Git repository» | `npm i -g backlog.md` | GIF борду, 6.6k зірок, доповіді з конференцій; **власного лендінга немає — домен веде на GitHub** |

**Три висновки, які змінюють структуру:**

1. **CTA — це команда встановлення, а не кнопка.** У Bun і Backlog.md команда стоїть у першому екрані й сама є конверсією. Розробник не «підписується» — він вставляє рядок у термінал. Одна дія, attention ratio 1:1 тримається.
2. **Секція прайсингу заміщається секцією ціни володіння.** У OSS платять не грошима, а вагою: розмір, час старту, залежності, ліцензія, що буде при видаленні. У нас саме тут найсильніші числа — 32 КБ, 80 мс, одна залежність, MIT.
3. **Соцпруф у категорії — не відгуки, а виміри.** Biome веде бенчмарком, Bun — чотирма бенчмарками, Zed — фідом комітів. Іменні цитати з'являються **після** того, як число довело тезу. Для нас це подарунок: у нас немає користувачів, але є виміри.

**Прямий конкурент лендінга не має взагалі.** Домен `backlog.md` робить 301 на GitHub. Тобто добре зроблена сторінка — це наша перевага в каналі, а не паритет.

## 3. Незручна правда: у нас немає соцпрува

Найважливіший розділ фреймворку — «логотипи й відгуки над згином» — для нас порожній. Зірок ~0, користувачів немає, іменних цитат немає. Ставити «Trusted by developers worldwide» не можна: це неправда, і HN-аудиторія розпізнає це за секунди.

Чим замінюємо, за спаданням сили:

| Замінник | Що конкретно | Звідки |
|---|---|---|
| Виміряний доказ тези | 8 396 злиттів у 130 репозиторіях; конфлікти в задачах у 15% репо; 89% — саме `content` | [probe-a-results.md](probe-a-results.md) |
| Виконуваний доказ | інтеграційний тест: троє правлять одну задачу на трьох гілках, злиття в будь-якому порядку, нуль конфліктів | `test/integration/merge.test.ts` |
| Числа, які падають при регресії | 32 КБ, 80 мс старт, 28 мс на 10 000 подій | тести продуктивності |
| Прозорість | 390 тестів, CI-бейдж, відкриті ADR із «що змусить нас переглянути» | `docs/decisions/` |
| Чесний статус | окремий блок «що перевірено, а що ні» | README |

Останній пункт — контрінтуїтивний, але для цієї аудиторії він сильніший за відгук. Жоден із чотирьох розібраних сайтів не пише, чого він **не** довів. Блок «Не перевірено: чи потрібна командам velocity — інтерв'ю ще не проведені» коштує нам частини конверсії й купує довіру, на якій тримається все інше. Ставимо його низько на сторінці, не в hero: чесність — не заголовок.

## 4. Рекомендована структура сторінки

Порядок за YC, три секції замінені під OSS. Пріоритет — номер завантаження контенту.

| # | Секція | Зміст | Анотації |
|---|---|---|---|
| 1 | **Hero** | H1 (outcome), підзаголовок (ICP + без чого), команда встановлення з копіюванням, під нею одне посилання «Quickstart», праворуч/нижче — вивід `sprint close` як статичний текст | єдиний головний CTA. Термінальний блок — справжній текст, не картинка: копіюється, індексується, важить нуль |
| 2 | **Micro-demo** | 40–50 с asciinema: `init` → `task add` → **`kadence ui`, рух задачі по колонках** → `sprint close`, який виводить `1.6h per point` | борд усередині демо, число — в останньому кадрі. Не автоплей, одне відтворення за кліком; постер — кадр із числом |
| 3 | **Problem → Transformation** | Before: «кожна команда оцінює в поінтах» → Agitate: «майже жодна не скаже, скільки поінт коштує; наступний спринт планується на відчуттях» → After: число виводиться з журналу, який команда вже пише | текст беремо з формулювань позиціонування, не вигадуємо нових |
| 4 | **Чому події, а не файли** | стан дрейфує · стан конфліктує · стан забуває | єдине місце з картками. Це головна диференціація проти Spec Kit, Beads і Backlog.md |
| 5 | **Доказ тези про злиття** | числа Probe A + посилання на інтеграційний тест і на сирі дані | це наш «logo strip». Ставимо високо саме тому, що заміщає соцпруф |
| 6 | **How it works** | три кроки: `init` → команди пишуть події → `sprint close` рахує. Схема `.kadence/` | другорядний CTA — «Read the docs» |
| 7 | **Ціна володіння** (замість Pricing) | таблиця: 32 КБ · 80 мс · 1 залежність · MIT · офлайн. Під нею риск-редьюсери | риск-редьюсери в термінах OSS: «Нічого не залишає машину», «Видалення — це `rm -rf .kadence`», «Ваші дані — файли, які читає будь-хто, і без нас теж» |
| 8 | **Для агентів** | `board --json`, `schema: "kadence/v1"`, `KADENCE_SOURCE=agent`, guide, який `init` пише сам | найкраще доведена потреба, але не унікальна — тому секція, а не заголовок |
| 9 | **Чесний статус** | що перевірено / що ні / відомі межі | окремий блок, візуально спокійний, без «але» |
| 10 | **Mini-FAQ** | 5 питань (нижче) | поруч із повторним CTA, а не окремою сторінкою |
| 11 | **Footer** | GitHub, npm, docs, ADR, ліцензія, changelog | |

Чого на сторінці **немає**: каруселі, попапа, email-гейту, порівняння з Jira й Linear, слова «трекер», логотипів компаній, яких у нас немає.

## 5. Копірайт для hero — три варіанти

Формула: *Outcome for [ICP] without [pain]*.

**A. Аналітика (відповідає чинному позиціонуванню — рекомендую)**

> **# Know what a story point actually costs your team.**
> kadence keeps tasks and sprints as plain files in your git repo, and derives velocity — and hours per point — from the journal your team already writes. No server, no account, no timesheets.

Outcome — «знати справжню ціну поінта». ICP — команда, що веде задачі в репо. Pain — «без таймшитів». Рівень читання: 7 клас.

**B. Git-native**

> **# Your sprint board lives in the commit.**
> Check out a release from three months ago and the tasks are exactly as they were that day.

Сильний образ, але це доказ, а не обіцянка: подія рідкісна й непомітна. Тримаємо секцією 4, не заголовком.

**C. Агенти**

> **# Task tracking your agents can read — no MCP server, no token, no network.**

Найкраще доведена потреба, але тут ми не унікальні: у Backlog.md є MCP, у git-issues — `.agent.md`. Кандидат на окрему сторінку `/for-agents` пізніше, не на головну.

**Ухвалено 2026-09-04 — меседж замінено.** H1 більше не про ціну поінта, а про спільний контекст:
> **Your team and your agents, working from the same context.**

Причина — у [перегляді позиціонування](../product/positioning-review-2026-09.md): ніша «робота в репо» виявилась зайнятою, а незакритою лишилась втрата контексту між сесіями. Варіанти B і C нижче збережено як історію рішення; velocity тепер живе в секції 6 як наслідок журналу. Це рівно те, що вирішило позиціонування після Probe A — не змінюємо рішення на етапі верстки.

**Головний CTA:**
```
npm install -g kadence
```
Кнопка копіювання, під нею одним рядком: `then kadence init` → посилання Quickstart. Другорядне «View on GitHub» — у навігації, візуально тихіше.

## 6. Mini-FAQ (заперечення, які реально прилетять)

1. **Це ще один трекер? У нас Jira.** Ні. kadence не замінює Jira для компанії — він дає команді число, якого в Jira немає без ручного заповнення. Живе поруч.
2. **Що воно робить із моїм репозиторієм?** Створює `.kadence/` і дописує туди файли. Нічого не редагує, нічого не видаляє, жодної git-команди від вашого імені.
3. **Чи побачать мої задачі сторонні?** Ні. Мережі немає взагалі, телеметрії немає. Це перевіряється: вимкніть інтернет.
4. **Що буде, якщо ми передумаємо?** `rm -rf .kadence`. Дані — звичайні JSON-файли, читаються без kadence.
5. **Чому не GitHub Issues?** Вони не йдуть за гілкою, не мають спринтів і не рахують velocity. І їх не видно офлайн.

Формат за фреймворком: одне речення + посилання на повну відповідь.

## 7. Лендінг як probe

Позиціонування прямо каже: ставка на velocity не перевірена, Probe B (інтерв'ю) не проведено. Лендінг — найдешевший спосіб отримати перший сигнал, і його варто спроєктувати як вимірювання, а не тільки як вітрину.

**Що вимірюємо:**

| Сигнал | Як | Що означає |
|---|---|---|
| CTR на копіювання install | подія на кнопці | базова конверсія сторінки |
| Скрол-глибина до секції 5 (докази) vs секції 3 (проблема) | скрол-мітки | чи тримає меседж «аналітика» |
| Клік «Read the docs» проти кліку на секцію «Для агентів» | події | **головне**: чи ходять по velocity, чи по агентах |
| Зірки/issues після заходу з HN | GitHub | якість трафіку |

Якщо трафік системно тікає в секцію «Для агентів», а не в velocity — це той самий сигнал, який мала дати Probe B, і позиціонування треба переглядати до того, як писати наступні матеріали.

**Напруга, яку треба назвати вголос:** продукт свідомо без телеметрії, а сайт із аналітикою. Це нормально й це різні речі, але FAQ має сказати прямо: «Сайт рахує анонімні перегляди. CLI не робить жодного мережевого запиту».

## 8. Технічні вимоги

- Статика, без фреймворка. Бюджет: < 2 с на 3G, < 50 КБ критичного шляху. Термінальні блоки — текст із CSS, не PNG.
- Шрифт: системний стек + один моноширинний. Жодних веб-шрифтів на критичному шляху.
- Тема: світла й темна за `prefers-color-scheme`. Аудиторія сидить у темній.
- Один H1. Title < 60 символів, meta < 155. Чисті URL: `/`, `/docs`, `/compare/backlog-md`.
- FAQ schema markup для сніпетів.
- Доступність: контраст 4.5:1 у термінальних блоках (найчастіша помилка dev-лендінгів — сірий на майже-чорному), фокус видимий, демо не автоплеїться.
- Хостинг: **Vercel, власний домен** (ухвалено 2026-09-03). Сторінка живе в тому ж репозиторії, тому числа в таблиці беруться з тих самих тестів, що падають при регресії. Vercel Analytics вимкнути на користь чогось, що не ставить куки — інакше доведеться питати згоду й ставити банер на сторінці, яка обіцяє «нічого не залишає машину».

## 9. Порядок дій

1. Написати копію повністю (усі 11 секцій) — до верстки, content-first.
2. Записати asciinema-демо, у якому останній кадр — `1.6h per point`.
3. Зверстати статику, виміряти бюджет.
4. Поставити події з розділу 7.
5. Тільки після цього — канали: Show HN, Lobsters, r/devtools, npm-сторінка, awesome-lists. Сторінка має бути готова до першої хвилі, бо другої з HN не буде.
6. `/compare/backlog-md` — окремою сторінкою після запуску: bottom-funnel інтент, у прямого конкурента лендінга немає взагалі.

**Ухвалено 2026-09-03:**

| Питання | Рішення | Наслідок |
|---|---|---|

| Демо | **Знімаємо з `kadence ui`** | Борд усередині демо, останній кадр — `1.6h per point`. Секція 4 отримує статичний кадр борду замість динамічного |

**Ризик рішення про демо, і як його знімаємо.** README чесно каже: TUI перевіряється руками, юніт-тестами покритий лише роутер клавіш (`src/tui/keys.ts`). Демо показуватиме найменш перевірену частину продукту, і чотири TUI-баги вже одного разу проїхали повз зелений набір тестів. Тому перед записом:

1. пройти сценарій демо руками щонайменше тричі, у тому самому розмірі вікна, у якому пишемо;
2. тримати в кадрі лише те, що є в сценарії — рух між колонками, деталі задачі, вихід. Без редагування полів, без миші, без фільтра;
3. якщо на записі щось смикнулось — не монтувати, а лагодити й перезаписувати. Змонтований баг усе одно приїде в issue;
4. перезнімати демо після кожної зміни в `src/tui/` — пункт унесено в чек-лист публікації.

**Лишилось невирішеним:**

- **Домен — вирішено 2026-09-04:** `kadence.dev` зайнятий, як і решта очевидних варіантів — ім'я належить WordPress-бренду Kadence WP. Беремо `kadence.tools`. Наслідки для SEO записані в [візуальному напрямі](../design/brand-and-visual-direction.md), розділ 11.
- **Хто пише англійську копію начисто.** Чернетку всіх одинадцяти секцій зроблено: [landing-copy.md](../product/landing-copy.md). Потрібне вичитування носієм або хоча б другий прохід на рівень читання.
