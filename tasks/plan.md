# План розробки FlowIt 0 → 1

- **Дата:** 2026-09-02
- **Джерела:** [SPEC.md](../SPEC.md) · [ADR-001…005](../docs/decisions/) · [state-machine](../docs/design/state-machine.md) · [edge-cases](../docs/design/edge-cases.md)

## Огляд

Від порожньої теки до `npx flowit`, яким можна вести спринт. Вісім модулів зі SPEC розкладені не горизонтально (спершу все ядро, потім весь CLI), а **вертикальними зрізами**: кожен milestone закінчується командою, яку можна запустити руками.

## Ключові рішення, що впливають на порядок

| Рішення | Наслідок для плану |
|---|---|
| Ядро без рантайм-залежностей ([ADR-003](../docs/decisions/003-zero-runtime-deps-in-core.md)) | ULID і валідація пишуться самі, у Milestone 1, під property-тестами |
| Синхронне ядро ([ADR-005](../docs/decisions/005-sync-io-and-snapshot.md)) | Немає async/await у `core/` — простіше тестувати |
| `state.json` обов'язковий | Milestone 3 не косметичний: без нього не виконується guardrail 200 мс |
| Первинний ID — ULID, `FLOW-N` похідний ([Probe A](../docs/research/probe-a-results.md)) | Нумерація рахується при згортанні, а не при створенні — впливає на M3 і M5 |
| Спринти — головний диференціатор ([positioning](../docs/product/positioning.md)) | Milestone 5 не можна відкладати «на потім»: це причина існування продукту |

## Milestones

| # | Назва | Що працює наприкінці | Модулі SPEC |
|---|---|---|---|
| **0** | Каркас | `npm test` і `npm run build` проходять на порожньому проєкті | — |
| **1** | Перша подія | `flowit init` і `flowit task add` пишуть подію на диск | M1, M2, M6 (частково) |
| **2** | Борд | `flowit task list` і `task move` показують стан із журналу | M3, M5, M6 |
| **3** | Швидко | 10k подій читаються за ≤ 200 мс; є компакція | M4, M2 |
| **4** | Агент | `--json` зі стабільною схемою, `.flowit/README.md` | M7, M8 |
| **5** | Спринт | `sprint close` рахує velocity й розбіжність оцінки | M6, M3 |
| **6** | Злиття | Три гілки зливаються без конфліктів; CLI це показує | інтеграційні тести |
| **7** | Реліз | `npx flowit` працює з чистої машини | пакування |

**Milestone 6 — момент істини.** Саме там перевіряється теза продукту на реальному git, а не на спайку.

## Ризики

| Ризик | Вплив | Пом'якшення |
|---|---|---|
| Guardrail 200 мс не тримається на реальних репо | високий | Тест продуктивності вводиться в Milestone 3 і падає при регресії |
| Нумерація `FLOW-N` при згортанні виявиться повільною | середній | Рахувати разом зі згортанням, не окремим проходом; міряти в Milestone 3 |
| `cac` виявиться несумісним | низький | Ізольований у M6; заміна на `citty` — кілька годин ([ADR-004](../docs/decisions/004-cli-and-build-stack.md)) |
| Спринти без інтерв'ю — ставка наосліп | **високий** | Milestone 5 будується, але README не публікується до Probe B |

## Відкриті питання

- **Probe B не зроблено.** Milestone 5 реалізує функцію, потребу в якій не підтверджено. Це свідомий ризик, ухвалений при виборі варіанта A.
- Поріг компакції (скільки місяців «гарячі») — вирішується даними в Milestone 3.
- Чи потрібен `flowit board` у v0.1 — [пріоритизація](../docs/product/prioritization.md) каже так; фінальне рішення після Milestone 2.

## Definition of Done для кожної задачі

1. Тест написано **до** коду і він падав
2. `npm test` зелений повністю, не лише новий тест
3. `npm run build` без помилок
4. Жодної нової рантайм-залежності в `core/` без ADR
5. Публічні функції мають типи без `any`
