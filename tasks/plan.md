# План розробки kadence 0 → 1

- **Дата:** 2026-09-02
- **Джерела:** [SPEC.md](../SPEC.md) · [ADR-001…005](../docs/decisions/) · [state-machine](../docs/design/state-machine.md) · [edge-cases](../docs/design/edge-cases.md)

## Огляд

Від порожньої теки до `npx kadence`, яким можна вести спринт. Вісім модулів зі SPEC розкладені не горизонтально (спершу все ядро, потім весь CLI), а **вертикальними зрізами**: кожен milestone закінчується командою, яку можна запустити руками.

## Ключові рішення, що впливають на порядок

| Рішення | Наслідок для плану |
|---|---|
| Ядро без рантайм-залежностей ([ADR-003](../docs/decisions/003-zero-runtime-deps-in-core.md)) | ULID і валідація пишуться самі, у Milestone 1, під property-тестами |
| Синхронне ядро ([ADR-005](../docs/decisions/005-sync-io-and-snapshot.md)) | Немає async/await у `core/` — простіше тестувати |
| `state.json` обов'язковий | Milestone 3 не косметичний: без нього не виконується guardrail 200 мс |
| Первинний ID — ULID, `KAD-N` похідний ([Probe A](../docs/research/probe-a-results.md)) | Нумерація рахується при згортанні, а не при створенні — впливає на M3 і M5 |
| Спринти — головний диференціатор ([positioning](../docs/product/positioning.md)) | Milestone 5 не можна відкладати «на потім»: це причина існування продукту |

## Ризики

| Ризик | Вплив | Пом'якшення |
|---|---|---|
| Guardrail 200 мс не тримається на реальних репо | високий | Тест продуктивності вводиться в Milestone 3 і падає при регресії |
| Нумерація `KAD-N` при згортанні виявиться повільною | середній | Рахувати разом зі згортанням, не окремим проходом; міряти в Milestone 3 |
| `cac` виявиться несумісним | низький | Ізольований у M6; заміна на `citty` — кілька годин ([ADR-004](../docs/decisions/004-cli-and-build-stack.md)) |
| Спринти без інтерв'ю — ставка наосліп | **високий** | Milestone 5 будується, але README не публікується до Probe B |

## Відкриті питання

- **Probe B не зроблено.** Milestone 5 реалізує функцію, потребу в якій не підтверджено. Це свідомий ризик, ухвалений при виборі варіанта A.
- Поріг компакції (скільки місяців «гарячі») — вирішується даними в Milestone 3.
- Чи потрібен `kadence board` у v0.1 — [пріоритизація](../docs/product/prioritization.md) каже так; фінальне рішення після Milestone 2.

## Definition of Done для кожної задачі

1. Тест написано **до** коду і він падав
2. `npm test` зелений повністю, не лише новий тест
3. `npm run build` без помилок
4. Жодної нової рантайм-залежності в `core/` без ADR
5. Публічні функції мають типи без `any`

# Етап 2: за межами MVP (рішення 2026-09-03)

## Що змінюється в позиціонуванні

MVP будувався під розробника в терміналі. Тепер тримаємо **обидві** аудиторії: розробника і ПМ-а. Це означає, що редагування, призначення, борд і планування стають першокласними сценаріями, а не додатком.

Незмінним лишається: **офлайн, без акаунтів, без мережі**. Усе нове має жити у файлах репозиторію.

## Ключові рішення етапу 2

| Рішення | Обґрунтування |
|---|---|
| **Редагування опису через `$EDITOR`** | Багаторядковий текст у прапорці незручний; `git commit` привчив до редактора |
| **`delete` є, але це подія `task.deleted`** | Append-only: подія лишається, задача зникає з проєкцій. Справжнього видалення з історії немає й бути не може |
| **Цикл залежностей не відхиляється, а показується** | Відхилення залежало б від порядку злиття гілок і зламало б інваріант I1. Обидві події живуть, CLI попереджає |
| **Вкладення — тільки посилання** | Файли в git прямо суперечать guardrail розміру |
| **Кастомні статуси зберігаються подією** | `board.configured` у журналі; без неї діють сім стандартних |
| **TUI на blessed, ліниво** | 22 мс проти 146 мс в Ink; лінивий `import()` лишає `task add` швидким |
| **Борд інтерактивний одразу в TTY** | `--json` і не-TTY дають статичний вивід, тому конвеєри й агенти не ламаються |

## Ризик, який треба тримати в полі зору

Етап 2 подвоює поверхню продукту. Guardrail 200 мс лишається чинним для **неінтерактивних** команд, і тест продуктивності має це стерегти — інакше TUI непомітно потягне залежності в гарячий шлях.
