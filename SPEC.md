# SPEC — FlowIt v0.1a (ядро)

- **Дата:** 2026-09-02
- **Статус:** запропоновано, очікує схвалення
- **Джерела:** [PRD](docs/PRD.md) · [ADR-001…005](docs/decisions/)

## 1. Мета

Дати команді розробників трекер задач, що живе всередині Git-репозиторію: задачі рухаються разом із гілками, а конкурентні зміни зливаються без конфліктів. v0.1a — це ядро без TUI: журнал подій, згортання в стан, CLI і JSON-контракт для AI-агентів.

**Користувачі v0.1a:** розробник у CLI та AI-агент, що читає `--json`. Менеджер як персона з'являється лише з TUI у v0.1b.

**Готово, коли:** розробник у чистому репозиторії робить `npx flowit init`, створює задачу, рухає її, зливає дві гілки з конкурентними змінами тієї самої задачі — і отримує коректний стан без ручного втручання, вклавшись у 200 мс на команду.

## 2. Що вже вирішено і не переглядається

Ці рішення підкріплені вимірами й закриті в ADR — реалізація не має права їх мовчки змінювати.

| Рішення | Джерело |
|---|---|
| TypeScript + Node 20+, ESM, збірка esbuild | ADR-001 |
| Подія — окремий JSON-файл, без відступів | ADR-002 |
| Ядро без рантайм-залежностей; власні ULID і валідація | ADR-003 |
| CLI: `cac`; кольори/таблиці/frontmatter — власні | ADR-004 |
| Ядро синхронне; `state.json` обов'язковий, у `.gitignore` | ADR-005 |

**Бюджет продуктивності.** 200 мс на команду, з них 40 мс уже витрачає старт Node. Решта 160 мс — на все інше. Будь-яка зміна, що додає рантайм-залежність, мусить показати, скільки мілісекунд вона коштує.

## 4. Модулі в порядку збірки

### M1 · `core/event` — схема події

Фундамент. Усе інше залежить від форми події, тому вона фіксується першою.

```ts
type EventType =
  | 'task.created' | 'task.moved' | 'task.assigned'
  | 'task.commented' | 'task.updated'
  | 'sprint.created' | 'sprint.closed';

interface FlowEvent {
  id: string;          // ULID, 26 символів
  type: EventType;
  entity: string;      // FLOW-42
  actor: string;       // git config user.email
  ts: string;          // ISO 8601, UTC
  source: 'human' | 'agent';
  data?: Record<string, unknown>;
}
```

**Критерії приймання**
- `ulid()` дає 26 символів Crockford base32; 50 000 викликів — без колізій.
- **Монотонність у межах процесу:** якщо системний час не більший за попередній виклик, випадкова частина інкрементується. Відкат годинника не має ламати порядок подій.
- Для `t1 < t2` завжди `ulid(t1) < ulid(t2)` при звичайному порівнянні рядків.
- `validate()` повертає перелік невалідних полів, а не кидає виняток — зіпсована подія не має ронити команду.
- Невідомий `type` вважається невалідним, але **не помилкою читання**: подія з майбутньої версії пропускається з попередженням, а не ламає CLI.
- `parse()` на пошкодженому JSON повертає помилку з іменем файлу.

**Заборонено:** будь-який `import` поза `node:crypto`.

### M2 · `core/store` — журнал

**Критерії приймання**
- `append()` робить `mkdir -p` перед кожним записом. Це не оптимізується: Git не версіонує порожні теки, і `events/2026-09/` зникає при перемиканні гілок — відтворено двічі під час спайку.
- Запис атомарний: спершу тимчасовий файл, тоді `rename`. Перерваний процес не залишає напівзаписаної події.
- `readAll()` — синхронний обхід (ADR-005), повертає події, відсортовані за `id`.
- **Дедуплікація за `id`:** та сама подія, що потрапила у дві гілки через `cherry-pick`, застосовується один раз.
- **Корінь `.flowit/` шукається від поточного робочого дерева**, а не від головного репозиторію — інакше `git worktree` пише не туди (та сама помилка, що в issue #558 у Backlog.md).
- Пошкоджений файл не зупиняє читання: він потрапляє у список помилок, решта журналу читається.
- **Поріг системного пошкодження:** якщо нечитних подій понад 20% — це не одиничний збій, і команда завершується помилкою з підказкою `git checkout .flowit/`.
- `compact(beforeMonth)` зводить старі події в `archive/YYYY-MM.json` і видаляє вихідні файли лише після успішного запису архіву.

### M3 · `core/projection` — згортання в стан

**Критерії приймання**
- Згортання чисте: ті самі події в тому самому порядку завжди дають той самий стан.
- Порядок визначається `id` (ULID), а не `ts` — годинники різних машин не збігаються.
- Конфлікт двох подій про одне поле розв'язується як last-write-wins за `id`, і програна подія **лишається в історії** — вона видима в `flowit log`.
- Подія про неіснуючу сутність не ламає згортання (гілку з `task.created` могли ще не змерджити) — вона тримається в очікуванні.
- Тест на сценарій зі спайку: троє рухають ту саму задачу в трьох гілках → після merge стан детермінований, усі три наміри в історії.
- **`sprint.closed` розв'язується first-write-wins**, на відміну від решти подій (last-write-wins). Закриття фіксує факт, який міг бути вже опублікований, тому пізніше закриття з іншої гілки не переписує velocity. Ця асиметрія позначається в коді посиланням на [state-machine](docs/design/state-machine.md).
- Подія, що додає задачу в **закритий** спринт, відхиляється зі збереженням у журналі — інваріант I5.

### M5 · `core/entity` — задачі

Опис задачі — Markdown із frontmatter: він має добре виглядати в `git diff` і на GitHub.

**Критерії приймання**
- **Первинний ID задачі — ULID, а не `FLOW-N`.** `FLOW-42` — це похідний ярлик, який присвоюється детерміновано під час згортання журналу, за порядком ULID.
- Дві гілки, що створили задачі незалежно, після злиття мають отримати різні номери автоматично, без втручання людини.

> **Чому саме так.** Початкова редакція цієї специфікації казала «ID виводяться з журналу, а не з лічильника». [Probe A](docs/research/probe-a-results.md) показав, що цього недостатньо: дві гілки, що розійшлися від спільного предка, бачать **однаковий** журнал і обидві виведуть `FLOW-42`. Merge-конфлікту не буде — події лежать в окремих файлах — але з'являться дві різні задачі з одним номером, і помилка буде тихою. Це саме та колізія, яку в реальних репозиторіях видно як `CONFLICT (add/add)` і яка висить відкритою задачею `task-4.12` у беклозі Backlog.md.
- Парсер frontmatter читає лише `key: value` до закривального `---`; усе інше — тіло опису.
- Двокрапка у значенні (`title: Fix: bug`) парситься правильно.
- Файл без frontmatter читається як задача з порожніми полями, а не як помилка.

### M4 · `core/snapshot` — кеш

**Критерії приймання**
- **Видалення `state.json` завжди безпечне.** Стан після видалення й перебудови ідентичний стану до нього. Це головний тест модуля.
- Інвалідація за `id` останньої врахованої події.
- Пошкоджений або нечитаний `state.json` мовчки ігнорується й перебудовується.
- Снапшот ніколи не комітиться: `init` дописує його в `.gitignore`.
- Guardrail: холодне читання 10k подій ≤ 200 мс, тепле (зі снапшотом) ≤ 20 мс.

### M6 · `cli/commands`

```
flowit init                       створити .flowit/, дописати .gitignore

flowit task add "<назва>"         нова задача
    -d, --description <текст>     опис
    --type task|bug|story         тип
    --priority low|normal|high|urgent
    -a, --assignee <хто>          виконавець
    --label <мітка>               мітка (можна кілька)
    --estimate <пункти>           оцінка — завжди останньою
flowit task list [--status=]      список
flowit task show <id>             деталі, поля й історія
flowit task move <id> <статус>    змінити статус
flowit task assign <id> <хто>     призначити; `none` знімає

flowit board                      канбан у терміналі
    -a, --assignee <хто|me>       лише чиїсь задачі
    --sprint                      лише активний спринт

flowit sprint create "<назва>"    перший стартує; наступні плануються
flowit sprint add <id> [--sprint "<назва>"]
flowit sprint start ["<назва>"]   запустити запланований
flowit sprint close               закрити активний і порахувати velocity
flowit sprint status              прогрес активного
flowit sprint list                усі спринти
```

### Поля задачі

Зведення Issue Type з Jira до того, що реально різниться. Усі поля, крім
назви, необов'язкові — старі події лишаються читаними.

| Поле | Значення | За замовчуванням |
|---|---|---|
| `title` | назва | обов'язкове |
| `description` | повний опис | порожньо |
| `type` | `task` · `bug` · `story` | `task` |
| `priority` | `low` · `normal` · `high` · `urgent` | `normal` |
| `labels` | довільні мітки | порожньо |
| `assignee` | виконавець | не призначено |
| `reporter` | автор `task.created` | автоматично |
| `estimate` | оцінка в пунктах | порожньо |

**Опис живе в події, а не в окремому markdown-файлі.** Файл на задачу — це
змінюваний стан, і він повернув би нам рівно ті `CONFLICT (content)`, які
становлять 89% реальних конфліктів за [Probe A](docs/research/probe-a-results.md).

**Порядок полів навмисний:** спершу суть задачі, потім класифікація, і лише
наприкінці оцінка. Так само в `task show`.

**Критерії приймання**
- Будь-яка команда поза Git-репозиторієм дає зрозумілу помилку, а не стек викликів.
- Команда до `init` пропонує запустити `init`.
- `actor` береться з `git config user.email`; якщо не налаштовано — помилка з підказкою, як налаштувати.
- `source` = `agent`, якщо виставлено `FLOWIT_SOURCE=agent` або присутня змінна середовища CI.
- Кожна команда, що змінює стан, дописує рівно одну подію.

### M7 · `cli/output`

**Критерії приймання**
- `--json` дає стабільну структуру з полем `schema: "flowit/v1"` — контракт, на який агент може покластися.
- У режимі `--json` у stdout немає нічого, крім JSON: попередження йдуть у stderr.
- Кольори вимикаються за `NO_COLOR`, `--no-color` і коли stdout не TTY.
- Код виходу: `0` — успіх, `1` — помилка виконання, `2` — помилка в аргументах.
- Таблиця не ламається на кириличних назвах і емодзі.

### M8 · `agent/contract`

**Критерії приймання**
- `init` створює `.flowit/README.md` з описом команд і формату `--json`.
- Наявний `AGENTS.md` доповнюється секцією FlowIt; те, що написала людина, не перезаписується.
- Повторний `init` не дублює секцію.

## 5. Стиль коду

- Строгий TypeScript: `strict: true`, без `any` у публічних сигнатурах.
- Ядро — чисті функції над явним станом; жодного глобального стану й синглтонів.
- Ядро не знає про `process.stdout`, кольори й аргументи: усе введення-виведення живе в шарі CLI. Перевірка — ядро має бути придатним до вбудовування як бібліотека.
- Коментувати причину, а не дію. Кожен неочевидний хід (`mkdir -p` при кожному записі, сортування за `id` замість `ts`) супроводжується посиланням на ADR.
- Помилки — типізовані результати на межах, винятки лише для справді виняткового.

## 6. Тестування

`vitest`. Не жене за відсотком покриття — покриває ризики, знайдені спайком.

| Рівень | Що покриває |
|---|---|
| Модульні | ULID, валідація, frontmatter, згортання |
| Property-based | ULID: монотонність і унікальність на 100k; згортання: детермінованість при перестановці порядку читання |
| Інтеграційні на реальному Git | Три гілки з конкурентними змінами → merge → детермінований стан. Це відтворення сценарію спайку й головний тест продукту |
| Продуктивність | 10k подій: холодний старт ≤ 200 мс, теплий ≤ 20 мс. Падіння тесту = регресія guardrail |
| Стійкість | Пошкоджений JSON, обрізаний файл, зниклий `state.json`, відсутня тека `events/`, подія невідомого типу |

**Правило:** кожен баг спершу відтворюється тестом, потім виправляється.

## 7. Межі

**Завжди**
- Дописувати в журнал, ніколи не редагувати й не видаляти події.
- `mkdir -p` перед кожним записом.
- Тримати `state.json` похідним: його видалення безпечне за визначенням.
- Міряти час команди при кожній зміні ядра.

**Спитати перед тим, як робити**
- Додати рантайм-залежність — навіть маленьку. Потрібен вимір вартості імпорту.
- Змінити форму `FlowEvent` або структуру `.flowit/` — це ламає чужі репозиторії.
- Змінити контракт `--json` — на нього спираються агенти.
- Виконати будь-яку команду Git, що змінює стан репозиторію користувача.

**Ніколи**
- Не комітити й не пушити від імені користувача. FlowIt пише файли; що з ними робити — вирішує людина.
- Не робити мережевих запитів. v0.1a працює повністю офлайн, телеметрії немає.
- Не чіпати `.git/` напряму — тільки через `git` CLI.
- Не писати `state.json` у Git.
- Не переписувати історію журналу «для порядку».

## 8. Поза скоупом v0.1a

TUI, веб-інтерфейс, синхронізація з GitHub Issues, багатокористувацькі права, вкладені підзадачі. TUI (M9) — наступний етап; жоден модуль ядра не має знати про рендеринг.

## 9. Відкриті питання

| # | Питання | Коли вирішувати |
|---|---|---|
| 1 | Стратегія при `rebase`: переписані ULID-и лишаються валідними, але чи не порушиться порядок | До першого релізу — потрібен тест на rebase |
| 2 | Поріг компакції: скільки місяців тримати «гарячими» | Після перших реальних репозиторіїв |
| 3 | Ідентичність, коли `user.email` різний на машинах однієї людини | v0.1b, разом із TUI |
